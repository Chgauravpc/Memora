# Benchmarking Memora Against Real Benchmarks

Status: **plan only — nothing here has been run.** All numbers in "Expected results" are
predictions with stated reasoning, not measurements.

> **The LoCoMo harness described in Phase 1 is now implemented** — see
> [BENCHMARK_README.md](BENCHMARK_README.md) for how to run it, and `benchmarks/`.
>
> Two figures in Part 3 below are superseded by that document, which targets a specific
> 32-core Xeon Gold 6530 rather than a generic box:
> - LoCoMo wall clock is **~40 min – 1 h**, not the 3–6 h estimated here. That figure
>   assumed modest parallelism; with all 10 conversations running concurrently the ingest
>   phase fully overlaps and API throughput becomes the only limit.
> - Cost is **$7–9**, at the low end of the $5–30 range, and barely moves with escalation
>   rate — the reader's 3k-token context dominates the token bill, not extraction.
>
> The Groq **free tier cannot run LoCoMo at all**: ~8,000 calls against a ~1,000
> requests/day cap is a hard floor of ~8 days, and a daily cap cannot be parallelised
> around. This was not anticipated below and is the single practical blocker.

## Part 1: What benchmark is Memora currently built to demonstrate?

**None that is public or external.** A full-text search of the repo for `LoCoMo`,
`LongMemEval`, `MemGPT`, `DMR`, `Mem0`, `Zep`, `MSC`, `BABILong`, and `needle-in-a-haystack`
returns zero hits outside `.venv/`.

What exists instead is a **self-authored synthetic harness** (`evaluation/`, "Phase 5"),
described in `evaluation/README.md` as "RAGAS-style". Note *style* — the actual `ragas`
package is never imported; `evaluation/metrics.py` reimplements precision/recall/MRR by hand.

It measures four things:

| Slice | Metric | Target in `evaluation/README.md` |
|---|---|---|
| Extraction | precision / recall / F1 | P>85%, R>80%, F1>82% |
| Retrieval | context precision / recall, MRR, top-K | CP>90%, CR>85%, MRR>0.8 |
| Distance sweep | recall @ 10/50/100/500/1000 turns | 95/90/85/70/60% |
| Consolidation | decay, merge, promotion rate | merge>90%, promote>80% |

Test data is 200 generated conversations of 10–30 turns from
`evaluation/conversation_generator.py` (`seed=42`), plus one 1010-turn distance-sweep
conversation.

The headline claim the harness exists to support is in `RESULTS_FEBRUARY_2026.md`:
**100% recall at 1000 turns** (up from 0%), alongside 89.5% extraction F1, 80.1% context
recall, 575 ms mean processing, 294 ms mean retrieval, 13.3% LLM escalation.

### Why that headline number should not be trusted

Three findings from reading the harness, in descending order of severity:

1. **The 1000-turn test has almost no distractors.**
   `generate_distance_sweep_conversation` (`conversation_generator.py:304-371`) plants
   **exactly one memory per distance — 5 memories total** — and fills the other ~1005 turns
   with `FILLER_MESSAGES`: `"Hi there!"`, `"Thanks so much!"`, `"OK, got it."`. Those are
   precisely what Stage 1's `should_extract` rejects, so the store holds roughly 5 items at
   query time. Retrieval then returns up to `MAX_MEMORIES_TO_RETRIEVE = 50`
   (`config.py:63`) with `MIN_SEMANTIC_SCORE = 0.1` and a recency branch that bypasses the
   similarity floor entirely. Returning 5 of ~5 items into a 50-slot window is arithmetically
   forced. **100% recall here measures nothing about retrieval** — it confirms 5 < 50.
   A real benchmark puts hundreds of competing memories in the store.

2. **Grading is bidirectional substring containment.** Every matcher
   (`ExtractionMetrics._memories_match`, `RetrievalMetrics._memories_similar`,
   `DistanceSweepMetrics._memories_match`) accepts on `content1 in content2 or content2 in
   content1` after lowercasing. A retrieved value of `"python"` matches a ground truth of
   `"prefers Python over JavaScript for backend work"`. Short values match almost anything,
   which inflates precision and recall in the same direction.

3. **Ground truth is generated by the same templates the regexes were written against.**
   `conversation_generator.py` fills sentence templates from fixed word lists; Stage 2's
   pattern tables were tuned on that same phrasing. Extraction F1 of 89.5% is substantially a
   measurement of regex-matches-own-template. `RESULTS_FEBRUARY_2026.md:98-110` documents
   what happens off-template: on a payment-domain corpus, "Phase 2 Extraction: 0%" and
   Stage 3 fired on ~100% of turns until payment patterns were hand-added. **This is the
   central risk for any real benchmark — every real benchmark is off-template.**

Also note the docs have drifted from `config.py` (per `CLAUDE.md`): the prose claims
`MIN_SEMANTIC_SCORE = 0.3` / `MAX_MEMORIES_TO_RETRIEVE = 10` / `MEMORY_TOKEN_BUDGET = 500`
against actual `0.1` / `50` / `3000`. The ASCII diagram in `RESULTS_FEBRUARY_2026.md:22` even
labels Branch 1 with the stale `0.3`. Any published comparison must re-derive its numbers
from `config.py`.

## Part 2: Which real benchmark, and the plan

### Choice of benchmark

**Primary: LoCoMo** (Maharana et al., ACL 2024 — *Evaluating Very Long-Term Conversational
Memory of LLM Agents*). Chosen for comparability: Mem0, Zep, LangMem, and most commercial
memory layers publish LoCoMo scores, so a number here is directly interpretable against
peers. Multi-session dialogue with per-session timestamps and QA categories for single-hop,
multi-hop, temporal, open-domain, and adversarial.

**Secondary: LongMemEval** (Wu et al., ICLR 2025). Better diagnostics — it isolates
information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and
abstention, which maps almost one-to-one onto Memora's Phase 3 superseding and Phase 4
consolidation. Use the `_S` variant (~115k tokens of history per question); `_M` (~1.5M) is
out of scope, see Part 3.

**Explicitly rejected:**
- **DMR** (MemGPT's 500-question set) — saturated near ceiling and widely criticized as
  unrepresentative; a good score proves little.
- **MSC** — superseded by LoCoMo on the same axis.
- **BABILong / needle-in-a-haystack** — measure long-context attention, not a memory layer.

> Verify dataset sizes from the downloaded files before quoting them. Public counts vary by
> release and by how the adversarial category is filtered; the estimates in Part 3 are
> deliberately given as ranges.

### Five blockers that must be fixed before any run is meaningful

These are architectural, found by reading the code, and each one silently corrupts results
if ignored.

**B1 — Memora cannot ingest assistant turns.** `process_turn(user_message, priority_types)`
(`memory_system.py:159`) takes one string with no role parameter. LoCoMo and LongMemEval are
two-sided, and a large share of evidence lives in the *other* speaker's turns. Feeding only
one side discards roughly half the ground truth. *Fix:* call `process_turn` once per turn for
both speakers, prefixing the speaker name into the text so extraction can attribute it. This
is an adapter-level workaround; correctly, `process_turn` needs a `role`/`speaker` argument.

**B2 — No way to inject the dataset's timestamp.** `timestamp` is in `MEMORY_FIELDS`
(`config.py:115`) but is stamped at ingest time. Both benchmarks date their sessions, and
temporal-reasoning questions are unanswerable without those dates. *Fix:* add an optional
`timestamp` / `session_date` parameter threaded to `store_memory`. Per `CLAUDE.md` this is a
four-place change (config field, `setdefault` in `store_memory`, cast in
`RedisStore.get_memory`, Qdrant payload). Without it, score the temporal category separately
and report it as not-attempted rather than as a failure.

**B3 — Redis is not user-namespaced, so runs cannot be isolated or parallelised.** Keys
`mem:`, `type:`, `dedup:`, `recent_memories` are global; `clear_memories()` wipes every user
and drops the whole Qdrant collection. Two conversations in flight at once will
cross-contaminate. *Fix:* one Redis logical DB (`db=0..15`) plus one Qdrant collection per
worker. This is also the unlock for the parallelism in Part 3 — without it the whole
benchmark is strictly sequential.

**B4 — There is no answer-generation or grading layer.** Memora returns context and never
generates; both benchmarks grade generated answers. *Fix:* build a reader (context +
question → answer) and an LLM judge. Use the benchmarks' own published judge prompts, not
new ones, or the numbers are not comparable.

**B5 — Retrieval is keyed on the current message.** Fine for QA (the question becomes the
query), but note `get_prompt_context` returns a **tuple**, not the `str` its annotation
promises (`memory_system.py:393-409`, flagged in `CLAUDE.md`). Unpack it.

Two lesser issues to record but not fix mid-run: access counts are double-incremented per
retrieval (`retriever` and `_compose_prompt_context`), inflating the frequency signal
(weight 0.05, so small); and `MEMORY_DECAY_ENABLED` is currently `False`, so the decay path
is untested — say so rather than reporting a decay result.

### Execution plan

**Phase 0 — Honest re-baseline (½ day, ~free).**
Before touching real data, make the existing harness informative: rerun the distance sweep
with ~500 memory-bearing turns instead of 5 filler-padded ones, and swap substring matching
for embedding similarity at a stated threshold. Purpose: establish how much of the "100% @
1000 turns" claim survives distractors. Expect a large drop. This is the cheapest
high-value experiment in the whole plan and it needs no API budget.

**Phase 1 — Harness (2–3 days, ~free).**
`benchmarks/locomo_adapter.py`: load dataset → replay sessions through `process_turn` in
order (both speakers, B1) → at each question call `get_prompt_context(question)` → reader →
judge. Fix B3 first so workers are isolated. Log per-turn escalation rate, latency, and
store size; escalation rate is the cost driver and you want it visible from turn one.

**Phase 2 — Smoke run (1 conversation, ~1 hour, <$1).**
Purpose is to catch the predictable failures early: does Stage 2 extract anything at all
off-template, or does Stage 3 fire on ~100% of turns (the `RESULTS_FEBRUARY_2026.md:98`
failure mode)? If escalation is ~100%, stop and re-cost — every downstream estimate scales
by ~7×.

**Phase 3 — Full LoCoMo.** Report per-category, not just aggregate. Aggregate hides the
bimodality predicted in Part 4.

**Phase 4 — LongMemEval.** Start with `_Oracle` (evidence sessions only) as a cheap
upper-bound on what the memory layer could achieve given perfect retrieval, then a
100–150-question `_S` subset. Report subset size and selection method; a subset score is not
a LongMemEval score.

**Phase 5 — Ablations,** only if Phases 3–4 produce a usable signal: hybrid on/off,
5-signal vs 3-signal, consolidation on/off, `MAX_MEMORIES_TO_RETRIEVE` sweep. These are the
results that would actually justify the architecture.

## Part 3: Compute required

Anchored on the repo's own measured numbers (`RESULTS_FEBRUARY_2026.md:395-412`): 575 ms mean
processing per turn, 294 ms mean retrieval, ~100 tokens/turn amortized at 13.3% escalation,
~$1.00 per 1000 turns.

**The dominant variable is escalation rate.** At the in-domain 13.3%, ingest is cheap. At the
out-of-domain ~100% the same doc reports pre-tuning, tokens/turn goes to ~750 and per-turn
latency to 1.1–3.2 s — a **~7× cost and ~3× time multiplier**. Both benchmarks are
out-of-domain for regexes tuned on personal-assistant and payment phrasing, so **budget for
50–100%, not 13.3%.** Ranges below span that.

### Hardware

No GPU required. `all-MiniLM-L6-v2` (384-dim) runs fine on CPU; extraction is a hosted API
call. Sufficient: 8-core CPU, 16 GB RAM, Redis + Qdrant via `docker-compose`, ~20 GB disk.
A GPU cuts embedding time only, which is not the bottleneck — the network-bound LLM calls
are. Watch instead for `_merge_similar_memories` (`consolidation_worker.py:223`), which does
pairwise comparison over a store that grows across a benchmark run, on the inline path every
`CONSOLIDATION_INTERVAL_TURNS = 50`. On a benchmark-scale store this may dominate wall clock;
measure it in Phase 2 before extrapolating.

### LoCoMo (~10 conversations, ~600 turns each ⇒ ~6k ingest calls, ~1.5–2k questions)

| Component | Estimate |
|---|---|
| Ingest wall clock, sequential | 1–4 h (575 ms–1.5 s × 6k, plus ~120 consolidation cycles) |
| Ingest tokens | 0.6M (13%) – 4.5M (100%) |
| Ingest cost, Groq `llama-3.3-70b` | **$1–5** |
| Reader (~2k q × ~3.5k ctx) | ~7M input ⇒ **$1** (gpt-4o-mini) / **$20+** (frontier) |
| Judge (~2k q) | ~1.4M ⇒ **$0.20** (mini) / **$5** (frontier) |
| **Total** | **~$5–30, 3–6 h wall clock** |

LoCoMo is cheap. There is no cost reason not to run it.

### LongMemEval

`_S` is ~115k tokens of history per question. At ~100 tokens/turn that is ~1,150
`process_turn` calls per question — the histories are not shared, so cost scales with
question count.

| Scope | Ingest calls | Sequential wall clock | Total cost |
|---|---|---|---|
| `_Oracle` (evidence only) | ~15–30k | 3–12 h | $5–20 |
| `_S`, 100-q subset | ~115k | 18–48 h | $30–80 |
| `_S`, full 500 q | ~575k | **90–240 h** | $60–400 |
| `_M`, full | ~7.5M | **months** | $1k–5k+ |

**`_S` full is borderline and `_M` is infeasible for this architecture.** Not because the
hardware is short, but because every conversation turn makes a *separate* extraction decision
— cost is linear in turns ingested, where a long-context baseline pays once per question.
That asymmetry is itself a finding worth reporting.

Fixing B3 (per-worker Redis DB + Qdrant collection) buys ~8–16× on an 8-core box, bringing
the 100-question `_S` subset to **2–6 hours**. Do B3 before Phase 4, not during.

### Recommended budget

**~$50 and ~2 engineer-weeks** covers Phase 0 through Phase 4-subset: LoCoMo in full,
LongMemEval `_Oracle` plus a 100-question `_S` subset. Most of the two weeks is adapter and
blocker work (B1–B4), not compute. Skip `_M`.

## Part 4: Expected results

Predictions with reasoning, so they can be scored against reality afterwards. Published
comparables on LoCoMo cluster around **60–75%** (Zep and Mem0 at the upper end, long-context
baselines mid-60s) — treat those as approximate and re-check current numbers before
publishing any comparison.

**Predicted Memora LoCoMo aggregate: 30–50%.** Below current published memory layers. Five
mechanisms, roughly in order of expected damage:

1. **Schema mismatch is the big one.** Memora extracts into seven fixed types
   (`config.py:60`) as flat `key`/`value` pairs. LoCoMo asks about narrative episodes — who
   did what, when, in what order. A `key`/`value` store of preferences and facts is
   structurally lossy for episodic narrative. An `event` type exists, but one string per
   event does not preserve sequence or causality.
2. **Off-template extraction (B-risk from Part 1).** Stage 2 patterns were written against
   the synthetic generator's phrasing. Expect Stage 2 near-zero and Stage 3 carrying almost
   everything — which is the cost blowup in Part 3 *and* a recall hit wherever Stage 3's
   500-token cap truncates.
3. **Temporal reasoning near floor (10–25%)** until B2 lands, because dataset session dates
   never reach the store.
4. **Multi-hop weak (20–35%).** Retrieval is a single flat weighted top-K with no query
   decomposition, no reranking, no iterative retrieval. Composing evidence across sessions is
   left entirely to the reader.
5. **Adversarial/abstention poor.** Memora always injects context and has no "I don't know"
   path; core memory is injected verbatim unconditionally. Benchmarks reward abstention on
   unanswerable questions.

**Where Memora should do genuinely well: single-hop user preferences and stable facts,
plausibly 60–80%.** That is what the type hierarchy (`type` weight 0.40) and always-on
`constraint`/`instruction` injection are built for, and the recency branch does give real
long-distance recall of whatever made it into the store. Expect a **bimodal profile** — which
is why Part 2 insists on per-category reporting. An aggregate near 40% would understate a
system that is decent at the narrow thing it was designed for.

**Predicted LongMemEval `_S`: 25–45%,** with `knowledge-update` the most likely bright spot —
Phase 3 superseding (`superseded_by`/`supersedes`) is a direct architectural match for that
category, and it is the one place Memora might beat a naive RAG baseline.

**The most likely single outcome of this whole exercise** is that the "100% recall at 1000
turns" claim does not survive the introduction of distractors — and Phase 0 will show that in
half a day, before any API spend. Expect recall@1000 to fall from 100% to somewhere in the
40–70% band once several hundred competing memories occupy the store. That is not a bug being
uncovered so much as a benchmark artifact being retired, and the resulting number will be
defensible in a way the current one is not.
